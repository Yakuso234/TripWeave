# TripWeave 初版实验规划

更新时间：2026-11-05（Asia/Singapore）

## 目标与授权

用户确认：SW 继续作为 Java 后端主项目；TripWeave 主要面向中国大陆校招 Agent 应用工程岗位。初版由 AI 助手负责设计和实现，用户在最小可规划版本完成后检查代码与实际结果并提出建议。本轮先规划落盘，再按优先级实现。技术选型必须有需求、发布源码/元数据和本机实验依据。

本版是项目的实验原型，不以功能齐全为目标。验收主线：输入一个城市、出发地点和少量要求，得到有地点和路线依据、可检查的结构化单日行程；至少支持一次需求变更，保留固定预约，展示结果与问题。

## 与桌面初步规划的关系

桌面 v1.0 的单城市两天、多轮修改、版本和提醒仍是项目中期方向。本次先缩小为单日、少量候选活动和一个固定预约的实验，优先验证 Agent 获取证据、生成、检查、按反馈修订的机制。两天完整规划、提醒、复杂恢复、长期偏好、多 Agent、RAG 和云部署不属于本次验收。

## 本轮优先级

1. P0：建立规范和记录；检查环境；用一个小型契约任务验证候选框架的结构化输出、工具调用、反馈修订和失败退出；解析并锁定依赖。仅比较必要能力，不建立两套完整应用。
2. P1：实现最小 Agent、地图适配、结构化需求/行程和确定性检查。明确区分真实模型/真实地图、真实模型/固定地图、固定模型/固定地图三种运行组合。
3. P2：提供本地 Web 输入与结果页面，支持一次变更和候选接受；保存需求与接受的行程版本。检查过时版本，保留固定预约。
4. P3：运行有意义的回归与端到端检查，整理启动方法、限制和用户审阅入口。真实凭据缺失时实现可继续，但真实接入验收保持受阻。

## 技术选型验证

候选主框架：PydanticAI；对照：DG 已采用的 LangGraph。FastAPI、Pydantic、SQLite、uv 为初版基础候选。只有在依赖解析与最小能力验证后，才在 ADR 中确认具体采用版本。

评价依据：工具参数与输出契约；模型反馈修订；上下文控制；请求超时与步骤上限；国产模型适配；已有知识复用与新增学习成本；本机可安装性和可复现性。新颖性不是单独的通过条件。

本版保留 SQLite 单库以减少环境门槛；业务状态与运行日志分工明确。PostgreSQL、AG-UI、OpenTelemetry 后端与持久执行引擎作为后续候选，不在最小原型中同时引入。

## 核心规则

- 查询地点后使用稳定地点 ID 和坐标；路线绑定起终点，活动修改后重查相关路段。
- 模型提出候选，程序检查固定预约、出发边界、活动时间和交通衔接。结构正确不等于事实正确。
- 结果区分通过、明确违反、信息不足；步骤耗尽不声称数学上无解。
- 固定样本和固定模型必须在界面、响应与报告中显示，不能算作真实 Agent 效果。
- 当前接受版本与候选分离；候选依据需求/行程版本，接受时检查有效性。
- 模型 Key 和地图 Key 只在本地配置，不写进源码、日志和聊天。

## 最低检查

- 一个正常规划和一次晚出门调整。
- 固定预约不被静默修改；交通不够时能反馈冲突。
- 模型使用不存在的地点、输出结构错误或工具失败时显式处理。
- 重复接受、过时结果和重启后读取当前行程的行为有检查。
- 记录模型、地图数据模式及测试结果，不把离线程序通过写成真实模型验证通过。
