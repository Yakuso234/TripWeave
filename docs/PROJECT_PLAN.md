# TripWeave 当前初版规划

更新：2026-11-17，Asia/Singapore。本文件替代初版离线范围；原构思保留在 PROJECT_PLAN_BASELINE_20261105.md，历史验证保留 PROTOTYPE_QA.md。

## 目标

面向中国大陆校招 Agent 应用工程，SW 承担 Java 后端主项目。用户授权助手设计实现，再由用户审阅。最新要求是实际根据输入和接口结果规划，内容包含住宿、餐饮与交通，界面采用顶部页面与分步偏好；DeepSeek 默认，凭据稍后提供。不能把固定输出当作产品功能。

校招版技术栈与演进路线见 [Agent 架构与技术栈](AGENT_ARCHITECTURE.md)。当前 LangGraph 负责证据查询、候选生成、校验和有限重试。

## 本轮交付范围

1. 单城市 1–7 天：结构化需求、真实地点、住宿位置推荐/手选、固定预约、必去景点、用餐、路线与时间校验。支持自定义住宿晚数（0 至天数减一），住宿按从首日起连续安排。
2. 新行程只支持高德＋DeepSeek。缺少任一 Key 时阻止生成；失败时显示原因。旧基础排程用于内部回归，历史行程仍可查看。
3. 五页工作台：概览、偏好、住宿、每日安排、接入设置；近期旅行和候选历史；接受与过时版本提示。独立修改页以指定历史方案和修改要求生成新候选。
4. 数据归属：SQLite 本地默认；SQLAlchemy Core 提供 PostgreSQL 可选适配。需求更新、候选、接受事件入库；并发写冲突拒绝，不覆盖其他请求。
5. 验证并同步选型、启动、限制与本地记忆。HTTP 模拟与真实 API 测试分别标记。
6. 协作入口先选景：本次偏好优先，复用新建时预填的长期兴趣，结合真实地图评分与城市代表性排序。每批最多 5 个，提供简短游玩介绍、适合人群与最多 5 张实景照片；不重复换批、保留选择、可回看。候选池与浏览进度入 SQLite。选景阶段不详细调查预约/票价/营业规则；排程发现关键事实缺失时才定向研究。
7. 确认选景时服务端冻结版本绑定的资料快照，原子更新需求；只交所选景点的精简介绍/来源给排程，已知体验组用于程序校验。修改目的地或所选地点会失效，重试复用资料，不重搜网页。交接后一次真实排程通过已有检查，现实营业/预约及餐饮质量仍未验收。
8. 已实现约束/事实合同与分类路由：多景点任选日期/完整停留窗口，精确预约、每日边界及固定交通必要条件预检；草稿交排程修订、关键资料交独立研究Agent补查、已知硬互斥请用户取舍，预算耗尽单列未完成。网页资料标web_reported且关键日期不能跨日复用。当前以真SDK＋HTTP模拟验证，已有一次真实研究回流，但草稿校验失败且修订预算耗尽，尚无新版可接受方案。
9. 未完成草稿、研究事实和错误随候选JSON存SQLite，可刷新/重启查看；无checkpoint、自动跨请求继续或任意节点恢复。按用户最新决定优先核心架构，质量/成本评估后置，保留8轮模型调用/180秒，研究一个阶段内最多恢复一次、合计5次搜索，不增加新框架与中间件。
10. 独立校验Agent在程序硬检查通过后检查完整多天需求与体验。最多一轮“初审意见→排程逐项修改或解释拒绝→程序再检查→校验复核”；仍不认同则前端展示双方理由、具体位置与未接受草稿，等待用户协调，不把模型分歧当需求无解。排程max、研究high、校验max，三角色共享8轮模型调用/180秒/最多检查3份草稿；不自动追加预算或真实测试。后续用户协调后的执行方式另行讨论，详见[校验协商](REVIEW_NEGOTIATION.md)。

## 验收主线

填写两天偏好 → 查询真实酒店 → 生成每天安排 → 检查预约和交通 → 接受 → 晚出门重新规划 → 旧候选不能覆盖新版本 → 刷新恢复，历史可查看。

没有凭据时可以完成界面、代码、HTTP 合同与数据库测试；真实模型、真实高德、真实完整端到端保持待验证。房价、空房与营业信息缺失不能用预算上限替代事实。

## 中间件决策

SQLite 已足够支撑当前单人本地阶段。PostgreSQL 为后续部署和多个规划请求并发准备适配，只有真实环境通过后才标记验证通过。Redis、消息队列、向量库与任务引擎待明确需求。现有排程、定向研究与独立校验三角色复用LangGraph/Pydantic AI；职责和成本边界见[多Agent方案](MULTI_AGENT_PLAN.md)，不因新增校验引入中间件。初始选景排序和推荐摘要仍为HTTP函数流水线。依据见 ADR-002，部署前提见 DEPLOYMENT.md。
