## 1 项目决定与目标

项目方向已经确定为旅游规划助手。接下来围绕实际功能推进，不重新循环讨论选题。SW继续承担Java后端项目的展示任务；DG保留代码和资料供按需参考，停止新增功能。本项目主要展示AI应用工程能力，同时保留必要的后端、数据和交互能力。

产品目标是让用户得到一份有真实信息支撑、能够检查和持续调整的短途行程，并在行程发生变化时同步后续提醒。用户不必在每一轮对话中重新描述酒店、预约和已经确认的安排。

项目的主要技术深入方向确定为：**多轮需求变化下的上下文组织与状态一致性**。重点研究模型每一步需要知道什么、哪些事实必须保留、怎样发现信息已经过期，以及怎样避免局部修改破坏整体安排。

这是一项求职项目建设方案。旅游助手已有同类产品，不能把题材、MCP接入或多角色数量本身写成创新，也不能提前声称优于现有完整AI产品。简历价值应由后续可演示的功能、实际问题、代码和验证证据支撑。

## 2 首个使用场景

用户计划在一个国内城市游玩两天，提供出行日期、住宿位置、兴趣、预算口径和已确认的预约。助手查询相关地点和路线，输出每天的时间安排、交通建议、来源及待确认事项。

行程确认后，用户提出：

> 明天晚出门一小时，尽量少走路。下午两点的预约保留，其他安排可以调整。

助手应读取原行程与预约，查询必要的新路线，识别受影响的安排，提供调整方案及变化说明。用户接受新版后，系统保存新版本并更新提醒。若条件无法同时满足，应说明冲突和可选取舍，向用户请求关键决定。

这个场景是首版验收主线。第一轮开发就应覆盖模型、真实工具和结构化行程之间的一条小链路，避免先做大量通用后台，再迟迟验证不了AI功能。

## 3 首版产品边界

### 3.1 输入

- 一个国内城市和连续两天的日期，采用旅行目的地的当地时区。
- 酒店或每日出发位置，以及返程时间等必要边界。
- 兴趣、出行节奏、交通偏好、可接受步行量等偏好。
- 预算及其包含范围，例如是否包含已支付住宿。费用区分已知金额、估算金额和未知金额。
- 用户明确提供的预约、固定活动及不可擅自变动的安排。首版手动输入，不要求读取邮箱、订单或支付账户。

缺少影响可行性的关键信息时先澄清。普通偏好允许使用明确展示的默认值，用户可以修改。不得悄悄把推测当成用户确认。

### 3.2 输出

- 按天展示的行程，包括地点、预计起止时间、移动方式与时间缓冲。
- 地点和路线的来源、查询时间，以及需要用户进一步核实的信息。
- 明确的约束检查结果。对于未知的开放时间、价格或预约要求，标为待确认。
- 修改后的行程版本，以及哪些内容改变、哪些确认安排得到保留。
- 与当前已接受版本对应的提醒清单。

### 3.3 暂不纳入首版

跨城长途交通购票、酒店和门票自动下单、支付、代取消真实预订、持续位置跟踪、全国所有景区覆盖、多人协作、多租户和复杂权限平台暂不纳入。预订由用户在原平台完成。

首版不保证行程全局最优、交通时间精确、主观体验最好，也不保证能从地图接口获取所有营业时间、预约规则和实时价格。

## 4 最小功能与验收

以下为计划验收条件，全部尚未实现。

| 编号 | 功能 | 首版可检查的结果 |
| --- | --- | --- |
| F01 | 理解并保存需求 | 从输入提取硬约束与偏好，保留原始输入关联；用户确认的预约有独立记录 |
| F02 | 查询真实信息 | 至少跑通地点搜索和路线查询；工具结果带来源、时间与状态，失败不会伪装为成功 |
| F03 | 生成并检查行程 | 返回可解析的结构化行程；检查时间冲突、交通衔接和已知硬约束；未知事实单独提示 |
| F04 | 多轮调整 | 基于当前版本修改；保持未被用户撤销的确认安排；展示变化与仍存在的冲突 |
| F05 | 保存与恢复 | 重新打开应用后仍能读取需求、接受的行程版本和待确认事项，无需依靠完整聊天记录重建 |
| F06 | 提醒与同步 | 当前版本的提醒可触发和查看；接受新版后，过时提醒取消或替换，服务重启后可重新加载 |

首版提醒采用**本地服务运行时的站内提醒中心**：后台任务检查到期提醒，页面打开时展示。服务关闭期间无法保证即时通知，重启后展示过期提醒。应区分已排期、已到期、已展示和用户已确认，不能将写入数据库等同于用户收到通知。

日历导出或飞书等外部通知作为后续扩展，一次接入一个渠道。静态日历文件导入不等于后续自动同步，不应宣传成双向日历集成。

## 5 信息与工具接入方案

首选高德官方开放能力验证地点、路线和天气查询。官方MCP文档列出了相关工具和地图唤端链接；这说明有接入基础，不代表本项目已取得权限或完成调用。[高德MCP概述](https://developer.amap.com/api/mcp-server/summary)

第一次接入需要确认账户、Key、权限、额度、返回字段和调用成本。优先选择能取得合法访问权限、字段足够、容易排查错误的接入方式。MCP适合标准化调用；若某项必要数据通过官方HTTP接口更合适，可由适配层统一封装，无需强行把全部模块做成MCP服务。

每条外部事实至少关联来源标识、查询时间、适用日期或范围。天气超出可用预报范围时不生成具体预报。路线耗时按估计值使用，并加入可配置缓冲；实际排队、临时闭馆等因素不能由模型保证。

开放时间、门票和预约信息若无法可靠获取，优先允许用户补充或提供明确来源并标注待确认。不把大规模抓取和网页解析设为首版的前置条件。

工具适配层统一区分正常结果、无结果、超时、限流、无权限和数据缺失。可以提供固定样本回放模式用于开发，但界面和报告必须标明数据模式。

## 6 上下文与任务状态设计

### 6.1 三类信息分开维护

**用户事实与确认状态**保存原始需求、硬约束、偏好、已确认安排和当前行程版本，是应用持久状态。聊天摘要只能帮助检索，不能覆盖这些结构化事实。

**当前任务上下文**由系统按需组装，包含本次变更、相关日期的安排、影响可行性的全局约束和少量工具结果。模型不必每轮看到所有历史消息和全部地点介绍。

**外部证据与运行记录**保存可追溯的工具结果和过程摘要，用于补充查询、回放和排查。外部文本按数据处理，不得变成修改系统规则的指令。

### 6.2 按语义选择信息

调整第二天上午时，应加载第二天的安排、下午预约、出发位置、返程边界和相关交通信息。第一天的长篇地点介绍通常可以省略；第一天是否已完成某个项目、是否影响总预算等关联事实仍可能需要保留。

因此，“切片”首先按任务、日期、地点、约束和依赖组织，再按模型上下文预算裁剪。禁止仅因字符数超限，就把预约、限制条件和对应内容切断。

### 6.3 变更处理

每次调整引用当前行程版本，生成候选变化，检查后再由用户接受。用户明确要求修改某个确认安排时可以更新，并记录来源；不能把“保持确认安排”做成永远无法修改的死规则。

接受新版时，保存行程和提醒更新意图；提醒触发前再核对版本是否有效。若数据已过期、并发修改导致版本不同或需求存在冲突，应重新检查或请求用户决定。

先实现单用户单任务场景，不以复杂分布式事务为前置目标。

### 6.4 值得研究的一个问题

在相同模型、工具和任务下，对比“累积完整历史”和“结构化事实加按需上下文”两种方案，观察硬约束遗漏、确认安排误改、输入Token和耗时。

实验应检查语义完整性，不能仅以Token更少作为优化成功。只有观察到实际问题，再增加摘要压缩、检索或更复杂的记忆机制。上下文工程的相关原则可参考官方实践；本项目效果需要独立验证。[上下文工程实践](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

## 7 建议技术结构

以下是初步建议，具体依赖版本在新会话核实兼容性并锁定。已经确定的是产品和工程边界，框架允许依据小型技术验证调整。

- Python服务承接模型调用、工具适配、上下文组装、检查与提醒任务。API可采用FastAPI，结构化输入输出可采用Pydantic。
- 首版一个主Agent，通过有限工具集合查询与修订；程序负责状态存储、确定性检查和副作用控制。应保留最大步骤、超时和失败退出边界。
- 运行时默认从轻量工具循环开始；若当前阶段确需持久checkpoint或跨进程执行恢复，再核实LangGraph等运行时是否更合适，选定后写简短ADR。用一个小任务检查必要能力即可，不建立两套完整Spike或同时维护两套主流程，也不为展示框架而引入多个Agent。
- 本地试用先采用SQLite持久化明确的需求、版本与提醒状态。若运行时另有checkpoint，必须写清其与业务表的分工和恢复来源，避免双重事实源。
- 前端采用简单Web工作台，展示输入、每日行程、证据、待确认事项、版本变化和提醒。可采用React与TypeScript，界面复杂度服务于功能演示。
- 日志与运行报告优先采用结构化文件和轻量界面；暂不强制部署完整监控平台、消息队列、向量数据库或微服务集群。

建议模块边界如下，最终目录由首轮技术验证确定：

```text
用户输入与变更
  → 需求和确认状态
  → 上下文组装
  → 模型与工具循环
  → 结构化行程和确定性检查
  → 用户接受当前候选版本
  → 版本存储和提醒任务

横向记录：来源与查询时间、工具结果、失败原因、用量与耗时
```

## 8 分阶段推进

### M0 真实工具与最小任务

先建立最小工程及必要记录文件。验证地点与路线接口，保存脱敏样本；让模型通过工具处理一个小任务并输出结构化安排。核实凭据、工具字段、运行时和持久化方案。

退出条件：一条真实调用链可运行，才完成M0的真实接入验收。无权限或缺少凭据时，明确记录阻塞并提供回放路径，可以继续不依赖真实接入的开发；真实接入验收保持受阻状态，回放成功不能替代它。

### M1 两天行程

实现需求保存、确认安排、行程生成和基本检查。界面可以简洁，先让完整任务可用。

退出条件：至少一个真实数据示例可展示；能发现故意构造的时间冲突和预约遗漏；来源未知的事实被明确标记。

### M2 多轮调整与上下文

实现版本管理、局部调整、上下文选择和冲突反馈。覆盖晚出门、降低步行、改变偏好和取消某项用户约束等场景。

退出条件：调整后保留应保留的事实，撤销已被用户修改的旧要求；若无可行安排，明确返回冲突。发生真实失败时保留定位与修复记录；未发生时记录实际设计取舍及验证，不要求为了面试素材制造故障经历。

### M3 提醒与恢复

实现站内提醒中心、后台调度、新版同步及服务重启加载。先把调度行为与模型生成解耦。

退出条件：旧版本的无效提醒不再正常触发；重启后状态可恢复；测试中可控制时间，不必反复等到真实出行日期。

### M4 演示与求职材料

整理稳定Demo、轻量验证报告、架构说明和少量有证据的工程复盘。复核README启动方法，以及用户本人对关键代码的理解。

退出条件：新会话或新环境可以按说明恢复开发；能展示生成、变更、检查与提醒的一条完整流程；简历描述与实际能力一致。

阶段按退出条件推进，不预先承诺工期。每阶段只选择一个当前最重要的可运行目标。

## 9 轻量验证方案

首轮准备约12个代表性任务作为开发起点，覆盖基础规划、缺失信息、预约保留、临时变更、条件冲突和工具失败。这个数量只用于初期发现问题，不证明统计可靠性。

具体期望从用户原始需求独立定义，不能只检查模型自己提取出的条件，否则模型漏掉某个要求后，检查仍可能通过。以后增加少量未用于调提示的保留任务，观察是否只适配了已知示例。

验证分为三层：

1. **固定数据回放**：工具结果固定，重复检查需求保持、时间关系、版本和提醒结果，降低外部变化造成的噪声。
2. **真实接口抽查**：检查权限、字段、来源与实际错误，抽查真实地点和路线。离线回放无法覆盖这些问题。
3. **人工试用**：判断行程是否易懂、节奏是否合理、修改是否减少手工工作。必要时用模型辅助点评，但不把模型自评作为唯一判据。

优先记录硬约束满足情况、确认安排误改、未解决事项、工具错误、输入输出Token和端到端耗时。缺少费用依据时只报告用量，不编造人民币成本。

上下文方案比较时，尽量保持模型版本、工具权限、数据和任务相同。对不稳定的代表性任务重复运行，并保留每次结果及失败，不能挑选最好的一次当整体效果。与现成旅行AI产品的对比另作探索，说明其权限和能力差异，不能混同为严格实验。

TravelPlanner提供了不依赖唯一标准行程的约束评测思路，但使用受控数据，不直接等于本项目的国内实时环境。[TravelPlanner](https://osu-nlp-group.github.io/TravelPlanner/)

验证随着功能成熟扩充，初期不要求先完成完整学术基准或大规模用户实验。[Agent评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 10 风险与应对

| 风险 | 首版应对 |
| --- | --- |
| 接口权限、费用或字段不能满足需要 | M0先验证；更换合适官方接入方式或调整该项功能，记录依据 |
| 营业时间、票价等信息缺失 | 显示来源及待确认状态，允许用户补充，不让模型补造事实 |
| 修改一处导致其他安排冲突 | 持久化全局约束，识别受影响依赖，检查候选版本后再接受 |
| 模型反复调用、超时或无法解决冲突 | 限制步骤和耗时，返回已有信息、未解决项和需要用户决定的部分 |
| 提醒重复或旧提醒仍触发 | 关联行程版本与稳定提醒标识，触发前核对有效性，明确重试语义 |
| 文档写得多但本人无法解释 | 每阶段只选少量关键问题学习，保留代码定位和独立讲解情况 |
| 不断加框架导致范围失控 | 先完成单Agent主线；新增技术须对应已经出现的需求和可检查收益 |

## 11 后续深度与扩展

第一优先级是上下文组织与变化处理。稳定后，可围绕数据时效、失败恢复、检索质量或用户偏好选择其中一个继续深入，不同时铺开。

跨行程偏好记忆需有用户可查看、修改和删除的机制；不能把一次旅行中的临时要求永久当作个人偏好。外部日历和通知需要确认权限、更新和失败恢复行为。多城市旅行需要重新检查跨城交通、住宿和日期约束，不能只放宽输入字段。

RAG、Skills、多Agent、向量检索等均作为有需求后再评估的选项。新增能力应说明它解决哪个实际问题、如何验证收益，以及新增成本。研究可从消融比较和失败归因开始，不要求训练模型或追求算法原创。
