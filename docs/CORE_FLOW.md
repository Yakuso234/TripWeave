# 当前核心链路与阅读备注

核对日期：2026-11-13。本文对应当前工作区，包含尚未提交的改动。当前已实现 **LangGraph分类编排＋排程Agent＋按需定向事实研究Agent**；初始选景排序与短摘要仍是HTTP函数流水线。两个Agent的职责与剩余边界见[多Agent架构](MULTI_AGENT_PLAN.md)，历史真实测试过程见[QA记录](evaluations/V02_QA.md)。

## 整体链路

```text
旅行需求（长期偏好只作新建默认值）
  ├─ 一键规划 ────────────────────────────────┐
  └─ 协作选景：高德召回→HTTP模型排序/分组       │
               →每批最多5项摘要/照片            │
               →用户勾选→原子确认资料快照 ──────┤
                                                ↓
LangGraph：preflight → prepare_evidence → propose → check_candidate
             │              │              │             │
             │              │              │             ├─通过→ready
             │              │              │             ├─草稿有错→propose局部修订
             │              │              │             └─仍缺关键事实/耗尽→明确结束
             │              │              └─明确资料缺口→research_information
             │              │                                  │
             │              │                                  ├─补齐→propose继续/修订
             │              │                                  └─未知/异常/耗尽→明确结束
             └─用户硬要求互斥┴─核实身份/必要交通后仍互斥→needs_user_decision
                                                ↓
                              保存结果/草稿/事实/问题至SQLite
                                                ↓
                              仅ready可接受，事务核对需求与接受版本
```

图中的预检、地图读取和业务检查是普通程序节点。研究和排程各有自己的Pydantic AI Agent、工具范围、消息上下文及结构化输出，共享本次规划的模型用量与运行时限。

## 一、需求与选景

`domain.Requirements`可类比Java请求DTO，`Itinerary/Stop`可类比输出DTO。Pydantic检查字段与基本格式；旅游事实和业务可行性需要后续证据及规则。

- 长期偏好存SQLite，新建时预填；本次需求快照和修订说明优先于一般兴趣、节奏及住宿偏好。
- `must_visit`、协作选中的原地点ID，以及`visit_constraints`都属于明确必去要求。原单项`booking_*`仍兼容，默认没有预约。
- `visit_constraints`最多10项，每项有稳定`constraint_id`、地点ID或明确名称、最短停留及一个或多个完整停留窗口。普通窗口任选一个；`fixed=true`是唯一精确预约窗口，必须按原起止时刻以`booking`安排。不能把“可用窗口”只理解成进门时间。
- 复杂自由文本`notes`仍会交给模型，但目前没有自动把任意自然语言规则可靠提取为结构化硬约束。重要日期/时间要求应填写结构化表单。

初始协作选景仍按既有流程：`discover_candidates`最多4个地图关键词、60个候选；`rank_candidates`一次模型HTTP请求排序并按输入主体ID分组；`make_batch`取未看过的最多5个体验，网页检索后整理短介绍与适合人群。照片来自高德，不发给模型识图。缺摘要/照片如实提示，耗尽只指本轮候选池。

源码入口：[attraction_picker.py](../tripweave/attraction_picker.py)、[attraction_research.py](../tripweave/attraction_research.py)。这些函数尚未迁移成自主推荐Agent，和下文按需事实研究是不同阶段。

## 二、确认选景：跨需求版本交接

客户端`confirm-attractions`只提交版本引用。服务端从SQLite读取勾选，原子冻结精简证据、增加需求版本并写事件，不信任客户端提交的摘要。立即重复确认幂等，旧版本拒绝，事务失败同时回滚。

`evidence.PlanningEvidence`保留来源需求版本、选择版本、目标需求版本及最多5项原ID/名称、介绍、人群、理由、来源与时间。全池体验组供程序查重；模型只获所选地点组ID及精简资料，不接收图片、全页网页、未选摘要或旧方案的重复快照。

目的地与所选ID/名称不变时可重新绑定需求版本；换城市或换点则清空。生成前再次核对当前版本与身份，失效快照在供应商调用前拒绝。这份选景资料用于了解游玩内容，不是营业或预约承诺。

## 三、五个LangGraph节点

实际入口是[real_planner.run_plan](../tripweave/real_planner.py)，图在`run_planning_graph`构建。

| 节点 | 当前动作 | 可能转移 |
| --- | --- | --- |
| `preflight` | 只看结构化用户要求。检查固定预约超每日边界、停留窗口均不足、已明确身份的固定预约重叠。无联网即可证明的冲突提前停止。 | 硬冲突结束；其余到`prepare_evidence` |
| `prepare_evidence` | 高德解析出发点、酒店、必去和约束地点，加载可信选景快照；按已核实身份再次预检，并核对固定承诺之间的必要交通。 | 硬冲突结束；其余到`propose` |
| `propose` | 排程Agent读取本次需求、证据和草稿，输出`Itinerary`，或输出具体`PlanningInformationRequest`。 | 行程到`check_candidate`；资料缺口到`research_information`；预算/范围错误结束 |
| `research_information` | 研究Agent只补指定地点、日期和字段，核对实际来源后将事实交回图状态。最多一轮。 | 事实齐备到`propose`；仍未知、服务异常或预算耗尽结束 |
| `check_candidate` | Python检查整份候选，以及已声明关键事实是否适用于实际安排日期。 | 通过结束；可修草稿回`propose`；关键事实仍缺失或轮数耗尽结束 |

地点必须唯一、身份正确；找不到就提示核对，不用附近地点替代。双方代码完整时比较城市代码，否则仅接受供应商返回的相同非空城市名。酒店只是位置候选，房价、房型和空房未确认。

必要交通预检只处理用户固定承诺：前一预约结束加地图耗时，必须不晚于后一预约开始；已确定的当天起点也检查到首预约的最低耗时。过夜后若酒店尚未手选，不拿程序推荐酒店强行证明用户要求无解。相同地点相同固定窗口可由同一站满足；同地点不同合法预约不会只因重复而被拒绝。预检通过只是未发现这些必要条件冲突，不是对所有组合做完整可行性证明。

## 四、两个Agent如何交接

排程Agent的工具是`lookup_places`、已知ID之间的`route`、`nearby_restaurants`；基于原方案修改时另有`find_place`。它不能支付、预订或自行放宽用户硬要求。

遇到关键资料缺口时，排程输出：

```python
PlanningInformationRequest(
    needs=[PlanningNeed(place_id="已知POI", day=2,
                        fields=["opening_hours", "last_admission"],
                        question="旅行当天的开放窗口和最晚入场是什么？")],
    reason="缺少这些资料会影响必去地点的安排",
)
# 这结束本次排程模型输出，由图决定是否允许研究；不是Agent自由聊天。
```

研究Agent接收城市、具体地点/馆区/地址、实际日期和所需字段。它用受限`search_place_information`查询，不接收整份草稿、原始私人备注或排程的全部消息历史。搜索范围不能由网页扩张，重复同一地点日期查询复用本轮结果。

`ResearchReport`中的`ResearchFact`必须绑定实际搜索来源编号、逐字连续摘录、地点和日期。程序拒绝无来源、摘录不在来源中、同字段重复/冲突、显式日期不适用等情况；结构化开放钟点必须出现在摘录中，查不到保持未知。资料传回排程时带来源、查询时间和`web_reported`标识。网页报告及其摘要不等于官方确认、未来一定开放或已预约；没有日期的通用说明也不能升级成未来保证。

只有明确提取出的`windows`、`closed`、`last_admission`用于程序时间校验，不从自然语言`value`正则猜完整时段，也不因“未查到”推断关闭。网页事实导致的候选错误交回排程或返回缺资料，不把模型解释当作已证硬互斥。

源码入口：[planning_contracts.py](../tripweave/planning_contracts.py)、[planning_research.py](../tripweave/planning_research.py)。

## 五、草稿修订与全程校验

`validate`检查地点ID、天数、活动数量、时序和地图最低耗时、必去、精确预约、结构化停留窗口、重复体验、过夜酒店收尾及预算预留。普通重复体验由模型取舍；已明确的用户重复预约保留。过夜日末站必须既为所选酒店ID，类型也为`hotel`。

已定位日期的草稿错误，给模型本次错误、目标日期的完整站点和其他天只读参考。模型返回需改日期的完整站点，程序合并后重新检查全程；不由程序自动顺延或跨天搬景点。无法定位的全局问题才基于最新完整草稿修订。

新研究事实可能影响原修订范围之外的日期，因此**补查返回后的首次修订**允许模型参考最新完整草稿输出完整行程。后续若只是已定位日期的错误，恢复局部修订，不因已有事实而永久改成全量重写。

模型曾声明某地点的某字段属于关键缺口后，不能通过把地点移到未补查日期绕过该要求；程序返回`critical_fact_date_missing`，已用完的一轮研究不会重新开启。这个保护只覆盖已声明的关键缺口，不证明模型已发现所有现实资料缺口。

时间含义：需求`start_time`为每日从当天起点出发的时刻；站点`start_time`为到达并开始本站，酒店亦然；上一站`end_time`为下一段最早出发时刻。站间留白分为路程、额外缓冲和明确休息，不能重复占用。纯休息用留白表达，不计正式活动；正餐供应未知时标注附近自选和待确认，不凭餐饮分类推定菜单。这些提示词说明不等于新增菜单或休息事实校验。

## 六、结果、持久化与接受

保留旧字段`status=ready/conflict`，新增`outcome`说明具体结束原因：

| outcome | 含义 |
| --- | --- |
| `ready` | 当前已知合同与程序检查通过，仍应阅读未核实项 |
| `needs_user_decision` | 用户明确硬要求之间，或与本次地图最低交通证据之间发现必要条件冲突，请用户调整要求 |
| `needs_information` | 关键资料仍缺失、第二次补查请求或换日后资料不适用，停止本轮研究 |
| `incomplete` | 请求/时限/候选轮数用完，或本次未得到有效结果；不表示需求无解 |
| `service_error` | 外部接口、地点解析或服务响应异常，本次未完成 |

`app.generate`把原需求与版本、最终结果、失败`draft`、`research_facts`、`issues`、轨迹及用量一起写入候选。捕获到的失败可保存已有草稿；没有草稿时保持空。数据库重启后可回看这些记录。`Store.accept_candidate`仅允许`ready`且需求/接受版本仍匹配的候选，事务内条件更新并写事件。

这属于候选结果持久化，**不是LangGraph checkpoint续跑**。进程在请求中突然退出时不能保证内存中的每一步已落库；当前没有自动从任意图节点恢复、后台重试或跨请求继续失败草稿的接口。

## 七、运行限额与验证边界

按用户最新决定，先完成核心架构，质量评测与成本优化后置。本轮未安装评测/优化框架。现有基线保留：一次规划默认最多6次模型请求、90秒、3轮候选校验；排程与定向研究共用同一`RunUsage`和限额，切换Agent不重置。定向研究最多1轮、最多5个地点日期搜索，同轮重复结果复用；地图本轮最多50次请求并缓存路线。模型请求和时限可由现有设置调整。

初始选景排序/摘要和用户主动换批属于其他请求，尚无贯穿选景到排程的整趟token/费用总账。共享模型请求上限不是人民币费用保证，也不代表模型质量已经评估。

当前验证：Python **256 passed、4 PostgreSQL skipped**；前端 **27 passed**，Ruff与格式通过。真SDK＋LangGraph使用HTTP模拟验证了研究回流、共享预算、局部/完整修订切换、关键日期缺口、固定预约交通预检，以及结果重启恢复。浏览器检查了时间要求表单与本机硬互斥分支，API回读为地图0次/模型0次，未接受候选。

本轮没有新增真实模型、地图或网页搜索；双Agent的真实模型协作行为仍待少量联调。当前本机服务为`http://127.0.0.1:8776/`，凭据只恢复到进程内。浏览器截图在`.runtime/architecture-time-form-20261113.jpg`，回读记录在`.runtime/architecture-ui-check-20261113.json`；两者是本机架构验收，不是真实旅游规划效果证明。旧真实案例及人工发现的问题保留在[QA记录](evaluations/V02_QA.md)。
