# TripWeave · 旅行规划工作台

> **免费额度试运行。** 核心图已接入排程与按需事实研究两个Agent，区分草稿修订、资料不足、硬要求互斥及本次未完成。新架构已通过HTTP模拟；11月14日真实样本已触发研究回流，但草稿未通过业务校验、修订额度耗尽，尚无新版可接受方案。详见[验证记录](docs/evaluations/V02_QA.md)。

偏好页可填写多条景点时间要求，包括任选日期、完整游玩窗口与最短停留。研究只补阻碍判断的已知地点/日期/字段，再交回排程；失败草稿及资料随规划记录保存到SQLite。当前提示词见[原文](docs/PROMPTS_CURRENT.md)，已实现架构与剩余边界见[双Agent链路](docs/MULTI_AGENT_PLAN.md)。质量评测和成本优化按用户决定后置，本轮未添加框架或中间件。

面向 Agent 应用工程的最小可规划实验。v0.2 将固定数据回放改为 **真实高德地图＋LangGraph 编排＋DeepSeek 工具调用**，提供中文分页工作台、1–7 天行程、住宿选择、餐饮与交通安排、约束检查、候选接受和规划历史。偏好页支持自定义天数、晚数、兴趣、节奏、交通、住宿取向和必去景点。保存偏好后可直接进入生成页，有住宿需求时可先手选酒店。行程摘要显示约束检查、必去景点安排和本次修订要求。打开通过检查的方案，可用「基于此方案修改」生成新候选。

**真实效果边界：** 上一版一次真实排程通过已有检查，但餐饮与备注仍有质量问题；新增研究回流已在真实模型中观察到，但最终草稿仍有活动、时间及重复问题；网页报告不等于旅行当天营业保证。产品无Key时阻止生成，不回退演示行程。v0.1离线实验保留在Git历史中。

## 启动

Windows PowerShell，在项目目录执行：

```powershell
uv --cache-dir .runtime/uv-cache sync --locked
.\start.ps1
```

打开 [本地工作台](http://127.0.0.1:8765/)。终端 Ctrl+C 停止。系统脚本策略阻止时，可运行 `.\.venv\Scripts\python.exe -m tripweave.launcher --port 8765`。

本轮本机实例运行在 [8776工作台](http://127.0.0.1:8776/)，使用 `.\start.ps1 -Port 8776` 可检查并复用同工作区实例，避免与旧项目端口重复。

本机验证环境 Python 3.14.7、uv 0.12.5。新机器需先安装 uv/Python 3.14。启动器核对工作区指纹：同目录已有服务时复用地址，其他项目占用端口则退出，不结束其他进程。检查用 `.\start.ps1 -CheckOnly`，换端口用 `.\start.ps1 -Port 8766`。

## 配置与使用

打开「接入设置」，填写高德 Web 服务 Key 和 DeepSeek API Key，点击保存。两个 Key 配置完成后，在行程页点击「用 DeepSeek 生成行程」。网页填写的 Key 只保存在本机服务内存中，刷新页面仍有效，重启服务后需要重新输入。要保留配置，可将 `.env.example` 复制为 `.env`（已有文件不要覆盖）：

| 配置 | 用途 |
| --- | --- |
| `AMAP_API_KEY` | 所有规划必需；高德 **Web 服务** Key，需具有 POI 搜索及路线权限 |
| `DEEPSEEK_API_KEY` | DeepSeek 模式必需；可在本机接入设置或 `.env` 配置 |
| `LLM_BASE_URL` / `LLM_MODEL` | 默认 DeepSeek 官方地址与 `deepseek-flash`；模型别名可修改 |
| `TRIPWEAVE_DATABASE` | 默认 `.runtime/tripweave.sqlite3`，本地无需额外数据库服务 |
| `DATABASE_URL` | 可选 PostgreSQL 连接串，优先于本地路径；详见部署说明 |
| `TRIPWEAVE_MAX_REQUESTS` / `TRIPWEAVE_RUN_TIMEOUT` | 默认 6 次模型请求 / 整次规划 90 秒 |

页面设置中的“已配置”只代表存在 Key，不代表权限、额度或连通性已验证。修改 API 配置后刷新页面配置状态；修改数据库连接后重启服务。

1. **旅行偏好**：城市、日期、人数、天数、出发点、节奏、每天时间边界、预算和固定预约，分三步填写。新建旅行的预约地点默认留空。指定的出发点、预约和必去景点需要匹配到唯一的高德地点。找不到或存在同名地点时，页面会提示核对名称。
   旅行偏好页顶部可打开「长期偏好」。已保存的设置会在新建旅行时预填，可在本次旅行单独修改。最后一步可选「一键生成行程」或「一起选景点」。协作选景每批最多 5 个，展示高德实景照片、真实评分、简短介绍与适合人群。照片可切换，来源可展开。「换一批」按原排序展示未看过的候选，已选景点保留，也能回看已浏览的景点。候选池、已看记录、摘要、来源和勾选都存入 SQLite，刷新可恢复。确认时由服务端原子保存版本绑定的精简资料，排程复用所选介绍与来源；选景与手填必去一并检查。
2. **住宿方案**：查询真实酒店 POI，按与出发点/预约片区的距离推荐，或手选。房价、房型和空房均待确认。
3. **每日安排**：DeepSeek 根据旅行偏好和地图证据提出候选，程序校验路线、时间和预约约束。过夜日末站须为所选酒店，站点类型须为 `hotel`。
   第3步的「景点时间要求」可添加最多10项必去要求，例如第1或第2天任选一天、10:00–13:00内完整游玩至少120分钟。固定预约仍可单独填写；API也支持多个精确预约。资料待补充、需要调整要求、本次未完成与接口异常分别显示，不能接受失败草稿。已知用户硬条件互斥在模型前停止；单纯重试耗尽不代表需求无解。
4. 检查每天景点、餐饮、路段耗时、住宿与待确认项，再接受候选。接受只保存本应用版本，不会订房或预约。
5. 修改出发时间或节奏并重新规划；旧候选保留原需求快照，过时版本不可接受。规划记录可以查看最近候选和失败；已接受方案刷新后恢复。

示例输入：上海、两天一晚、两人、人民广场 09:00 出发，每天 20:30 前结束、第一天上海博物馆 14:00–15:00 固定活动。真实地点由高德检索，不预先承诺输出某个景点或酒店；把出发改为 14:30 后固定预约会产生衔接冲突，不会偷偷改预约时间。

## 技术与数据

```text
分步偏好 / SQLite需求快照 → 用户硬要求预检
                               ├─ 已知硬互斥 → 请用户调整
                               └─ 地图地点/固定交通预检
                                          ↓
                                    排程Agent
                               ↙           ↘
                    关键缺口→研究Agent     完整候选
                               ↘           ↓
                              新事实→排程修订
                                          ↓
                       程序全量校验 / 定位问题 / 有限修订
                                          ↓
                      结果、草稿和事实入库 → 仅ready可接受
```

- `domain.py`：结构化需求与行程合同。
- `maps.py`：高德 HTTP 适配、来源时间、单次运行路线缓存、超时及响应校验。
- `attraction_picker.py` / `attraction_research.py`：兴趣与热门景点召回、模型排序与同一游玩内容分组、每批 5 个的网页摘要和可恢复选景状态。
- `evidence.py`：服务端确认后的精简资料合同、来源核验、需求版本绑定；不传图片和网页原文给排程。
- `real_planner.py`：LangGraph 规划图、DeepSeek 工具和约束校验。旧规则排程用于内部回归。
- `planning_contracts.py`：多日期时间窗、精确预约、资料请求/研究合同与确定性预检，网页资料只作为带来源报告。
- `planning_research.py`：独立研究Agent与受限搜索工具，核对来源/引文/日期和明确钟点后交回排程。
- `storage.py`：SQLAlchemy Core，SQLite 默认 / PostgreSQL 可选，事务内记录需求、候选和接受事件。
- `app.py`：API 编排、同源限制、业务错误响应；外部调用期间不持有数据库事务。
- `static/`：原生 HTML/CSS/JS，不需 Node 构建链；顶部五页与分步卡片。

需求与接受版本以数据库为事实源，不从模型对话摘要恢复。提交使用需求修订号和已接受版本共同检查，存储更新另有原子比较写保护。历史事件与变更在同一事务提交。当前聚合仍以 JSON 文本保存，未实现复杂跨行程分析或全套 schema 迁移系统；旧本地表和记录保留。

校招版目标与开源参考见 [Agent 架构与技术栈](docs/AGENT_ARCHITECTURE.md)。历史选型依据见 [Agent 运行时](docs/adr/ADR-001-prototype-stack.md)、[真实接口与数据库](docs/adr/ADR-002-real-planning-storage.md)。[后续部署要求](docs/DEPLOYMENT.md)。

当前代码的带备注说明见[核心链路](docs/CORE_FLOW.md)：选景函数流水线、可信交接、排程与按需研究两个Agent、分类结果与SQLite记录。单次规划两角色共享原6次模型请求/90秒，定向研究最多一轮/5个地点日期搜索；初始选景请求不包含在这个跨角色预算内。尚无图checkpoint或任意步骤续跑，失败记录持久化不等于自动恢复。质量/成本评估工具暂缓接入。

当前模型提示词原文、动态输入和结构化输出合同见[提示词说明](docs/PROMPTS_CURRENT.md)。用户显式时间要求可由程序核对，来源明确的网页窗口会进入草稿检查；自由notes仍由模型理解，尚未自动抽取成全部硬约束。

协作选景先用最多 4 次高德关键词查询召回最多 60 个候选，复用 `extensions=all` 返回的照片和评分，避免逐景点查询详情。模型只对候选池排序一次，结合本次需求、预填的长期兴趣、真实评分与定性的城市代表性。分组必须引用已知主体地点 ID；程序合并同组及传递关联，只保留排序最前的候选。未分组、未知主体或模型失败会明确报错，不降级展示未经去重的原始地图结果。每批只对新展示的最多 5 个景点检索短介绍，再统一生成摘要。预约、开放时间和票价不在选景阶段详细调查。评分只展示供应商实际返回值，知名度没有伪造数值榜单。[高德地点搜索](https://lbs.amap.com/api/webservice/guide/api/search/) · [DeepSeek Search](https://api-docs.deepseek.com/guides/search/)

照片最多展示 5 张，不足 3 张时说明实际取得数量，不复制凑数；缺少可靠摘要或适合人群时逐卡提示，推荐理由独立展示。候选看完仅代表本轮有限召回范围，不能理解为整座城市没有其他值得去的景点。旧版草稿在点击「查询景点」时按新规则重新分组，并保留原选择的地点 ID；失败不覆盖旧草稿。旧选择属于同一体验时可逐个取消，处理完重复选择后才能确认生成。模型配置缺失会在地图查询前提示，不消耗地图请求。

## 边界

- 酒店位置推荐不等于低价保证；住宿按用户上限预留，餐饮按 65 元/人/餐预留，门票、交通等实际费用为未知，不能宣称总费用已满足。
- 路线是查询时的估算；未验证未来日期营业、节假日、排队、公交班次和景区内步行。地点同名或分馆需人工确认。
- 排程是有限候选的启发式方案，不是全局最优；冲突或请求耗尽不意味着数学上无解。最后一天不默认回酒店或返回出发站。
- 无提醒、自动订单、支付、MCP、RAG、持久任务恢复或多用户鉴权；只监听 127.0.0.1，供本地单用户实验。仅配置 PostgreSQL 不等于可公开部署。
- `.env`、`.runtime`、私人记录不进入仓库；尚未指定项目开源许可证。未复制其他旅游项目实现代码，第三方依赖遵循其许可证。
